## 수정 내용
1. 펌웨어: 기존 `WALK <방향>`이 `controlArm(CTRL_SERIAL)` + `controlWalk`를 거친다 (1초 리스). 4way 노트북은 걷는 동안 0.25초마다 `HB`를 보내는 스레드를 돌리고 (`serial_lock`), CAPS에서 `LEASE1`을 요구한다.
2. Wi-Fi API에서 `hostOk()`: Host가 `192.168.4.1`/`192.168.4.1:80`이 아니면 403 `bad_host`.
3. 페이지: 0.75초 안에 받은 유효 상태가 없으면 하트비트를 보내지 않음. 상태 요청은 한 번에 하나만, 1.5초 뒤 중단. 게이트웨이는 ValueError를 잡아 `bad_status_reply`로 반환.
4. 웹 서버를 별도 FreeRTOS 태스크(코어 0)로 옮김. `controlMutex`를 loop와 핸들러가 공유 (네트워크 I/O 중에는 잡지 않음).
5. 게이트웨이: 핸드셰이크는 `_lock` 밖에서 (`usb_connecting`), STOP은 즉시 쓰고 잠금 아래에서 다시 확인. 폴링 중 재연결은 4초.
6. `_exchange`: 쓰기 전에 `reset_input_buffer()`, OK 응답은 줄 전체 비교.
7. `status()`: 실제 오류 코드 반환, `connected` = 포트 상태.
8. 상태가 오래되면 페이지에 "알 수 없음" / "-" 표시.
9. STOP 시 중립 복귀를 README, 페이지, 노트북에 명시.
10. `--host`는 IPv4 루프백만 허용.

테스트: 41개 통과 (모의 시계 리스 만료, 홈잉/Wi-Fi 제어 중 ARM 거부, STOP 즉시 쓰기, 줄 전체 비교, 오래된 상태일 때 하트비트 없음(Node 하네스), 펌웨어 정적 검사, web_page.h 최신 여부).

## IMU 값 안 나옴 → 주소 자동 복구 (2026-11-10)
- 증상: `IMU ready=1 addr=0x68 valid=0`. 부팅한 뒤로 값을 한 번도 읽지 못했다. I2C 스캔에서는 0x69만 보였고, 0x69에서 직접 읽으면 정상(az=1.00, PWR_MGMT_1=0x01)이었다.
  → 부팅 때는 0x68이었다가 나중에 0x69로 바뀌었다. **AD0 핀이 연결되지 않았거나(플로팅) 접촉이 불안정한 것**으로 추정한다. 하드웨어 수정 권장: AD0을 3.3V(0x69)나 GND(0x68)에 연결.
- RTS 리셋 후 0x69로 정상 동작했다 (valid=1, 기존 영점·축 설정 유지: rollmap=-Y pitchmap=+X).
- 펌웨어 `imu_sensor.ino`: `imuRecover()` 추가. 유효한 샘플이 0.5초 넘게 없으면 1초 간격으로 확인한다.
  - 빠른 전환(지연 없음): 깨어 있고 약 1 g를 읽는 같은 칩이 0x69/0x68에 있으면 그 주소로 바꾼다.
  - 칩은 그대로 깨어 있는데 값만 이상하면(흔들림) 아무것도 하지 않는다.
  - 다시 초기화(약 0.2초 블로킹)는 비활성화 상태이고, 걷지 않고, 부팅 복귀 중이 아닐 때만 한다 (`imuSafeToBlock`). 부팅 때 센서가 없었으면 같은 조건에서 2초마다 다시 찾는다.
  - IMU 줄 끝에 `recover=N`을 붙였고, 복구할 때 `IMU_RECOVERED ...`를 출력한다.
- 정적 테스트 추가 → 53개 통과. 컴파일 경고 없음 (76%).
- 2026-11-10 업로드 완료 (배선은 바꾸지 않음, 사용자 선택). 부팅: 0x69, valid=1, recover=0. 약 12초 동안 끊기지 않음. 주소가 실제로 바뀌었을 때 복구되는지는 아직 실물에서 보지 못함.
