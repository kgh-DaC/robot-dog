# 로봇개 엔지니어링 오케스트레이터

## 실행 모드: 지속형 전문가 협업

펌웨어, 텔레메트리, 브라우저 동작 또는 이들 사이의 인터페이스를 함께 바꿔야 할 때 이름이 있는 전문가를 조율한다. 기기와 웹 시스템은 계약에 대한 반복 피드백과 명시적 안전 검토가 필요하므로, 이를 한 번에 끝나는 맹목적 워크플로로 만들지 않는다. 단일 분야에 한정된 간단한 질문이나 변경은 해당 전문가만 호출한다. 일반 기능 작업에는 전문가를 최대 4명까지만 사용한다.

| 이름 | `subagent_type` | 담당 업무 | 스킬 |
|---|---|---|---|
| `embedded` | `robot-embedded` | MPU9250, INA219, 보행·서보 펌웨어, 기기 감시 타이머와 오류 | `robot-dog-embedded` |
| `telemetry` | `robot-telemetry` | 버전이 지정된 계약, 보안 게이트웨이 경로, 로깅, 에너지 분석 | `robot-telemetry` |
| `digital-twin` | `robot-digital-twin` | 브라우저 대시보드, 동작 렌더링, 인증된 제어 | `robot-digital-twin` |
| `qa` | `robot-integration-qa` | 독립적인 통합·안전·회귀 검증 | 공유 계약 및 관련 도메인 스킬 |

## 통신 및 작업 의존성

- 다음과 같이 이름이 있는 전문가를 실행한다: `Agent(name: "embedded", subagent_type: "robot-embedded", ...)`, `Agent(name: "telemetry", subagent_type: "robot-telemetry", ...)`, `Agent(name: "digital-twin", subagent_type: "robot-digital-twin", ...)`, `Agent(name: "qa", subagent_type: "robot-integration-qa", ...)`. 요청에 필요한 전문가만 사용한다.
- `TaskCreate`/`TaskUpdate`로 다음 의존성을 추적한다: **계약 합의** → **펌웨어 및 게이트웨이·로깅** → **대시보드 통합** → **QA**. 계약이 합의된 뒤 펌웨어와 게이트웨이·로깅은 병렬 진행할 수 있다. 대시보드는 소비할 필드가 안정된 뒤 시작한다. QA는 변경된 생산자와 소비자가 준비된 뒤 수행한다.
- 계약 제안과 결정은 `SendMessage`로 `embedded` 및 `telemetry`에 보낸다. 확정된 필드명, 단위, 최신성 규칙은 `digital-twin`에 전달한다. QA에서 근거가 있는 파일·필드 수준의 발견 사항이 나오면 담당 전문가에게 보내 집중 수정을 요청하고 해당 경계를 재검증한다.
- 에이전트가 유휴 상태이거나 응답하지 않으면 `SendMessage`로 상태와 한 번의 구체적인 후속 작업을 요청한다. 해당 시도가 실패하기 전에는 같은 작업의 중복 담당자를 실행하지 않는다.

## 확정된 프로젝트 선택

- 사용자가 호스팅 공급자를 선택하지 않으면 아키텍처는 클라우드 중립으로 유지한다.
- 인터넷을 통한 보행 제어를 포함하되 기존 ESP32 직접 WebSocket 제어 엔드포인트를 공개하지 않는다.
- 인터넷 접속은 인증 및 암호화된 사용자·기기 세션과 게이트웨이 또는 브로커를 거치게 한다. 권한 확인, 명령 허용 목록, 명령 최신성·재생 공격 방지, 장치 측 검증을 적용한다.
- 동작 전에 명시적으로 활성화한다. `STOP`은 항상 사용 가능하고 최우선이다. heartbeat 손실이나 치명적 오류는 동작을 정지시킨다. 재연결·재부팅 후 자동으로 동작을 재개하지 않는다.
- 사용자의 명시적 승인 없이 배포, 공용 엔드포인트 공개, 자격 증명 변경, 실물 로봇 동작 명령을 수행하지 않는다.

## 작업 절차

### 0. 현재 상태와 범위 확인

1. `esp32-robot-dog-code-master/software/robot_dog_esp32/`, `software/web/`, `modeling/` 및 관련 노트북에서 작업 대상 파일을 확인한다. 현재 프로젝트에는 Wi-Fi/WebSocket 제어, 브라우저 조이스틱, 기본 INA219 텔레메트리가 있으며 MPU9250 축 매핑은 불확실하다고 표시되어 있다. 기능이 이미 완성된 것으로 간주하지 말고 현재 코드를 직접 확인한다.
2. 기존 `_workspace/` 인계 자료를 확인한다. 첫 실행이거나 관련 없는 새 실행이면 여러 전문가가 참여할 때만 간결한 실행 폴더를 만든다. 한정된 변경은 중간 파일을 만들지 않는다.
3. 일부 재실행 요청이면 이전 결과를 읽고 영향받은 전문가만 다시 실행한 뒤 변경된 인터페이스를 QA한다. 새 입력이 이전 결과를 대체한다면 새 작업 전에 기존 폴더를 타임스탬프가 붙은 이름으로 보존한다.
4. 범위와 물리적 제약을 확인한다. 보드·센서 배선, 서보 보정, 배터리 화학 특성·셀 구성, 허용 기울기, 차단 기준, 샘플링 주기, 호스팅 공급자를 추측하지 않는다. 안전한 작업을 막는 값은 사용자에게 확인하고, 그렇지 않으면 설정 가능한 미확정 항목으로 명시한다.

### 1. 병렬 구현 전에 인터페이스 합의

1. 여러 분야에 걸친 기능이면 `telemetry`와 `embedded`를 함께 시작한다. [공유 텔레메트리 계약](references/telemetry-contract.md)을 바탕으로 호환 가능한 센서, 서보, 보행·오류, 명령 필드를 제안하게 한다.
2. 메인 에이전트가 제안을 조정해 단일 계약을 기록한 다음 `digital-twin`에 소비자 구현을 요청한다. 펌웨어와 UI가 각자 필드명, 단위, 명령 의미를 정하게 두지 않는다.
3. 펌웨어 전용 또는 UI 전용 요청은 무관한 전문가를 생략하되, 공유 계약을 유지한다.

### 2. 의존성에 따른 구현

1. 경계 합의 이후에만 서로 독립된 기기 및 게이트웨이·로깅 작업을 병렬로 진행한다.
2. 텔레메트리와 명령 계약이 안정되면 대시보드·디지털 트윈 작업을 시작한다. 기존 UI와 로봇 형상을 중복 구현하지 말고 활용한다.
3. 전체 작업이 끝난 뒤 한 번만 검사하지 말고 기기→게이트웨이, 게이트웨이→로그, 게이트웨이→UI 경계를 완성할 때마다 `qa`에 확인을 요청한다. 원격 제어 테스트는 모의 데이터나 시뮬레이터로 수행한다.
4. QA에서 계약 불일치나 안전 실패가 발견되면 근거를 담당 전문가에게 보내 수정을 요청한다. 영향받은 테스트와 통합 검사만 다시 실행한다. 수정은 최대 두 차례까지 반복하고 해결되지 않은 항목을 보고한다.

### 3. 검증 및 보고

- 저장소에서 사용할 수 있는 관련 펌웨어·웹 빌드, 단위·통합 테스트, 정적 검사를 실행한다. 의존성 명세를 바꾸지 않았다면 도구를 설치하지 않는다. 검증 도구가 없어 실패한 경우에만 필요한 설치를 고려한다.
- 소프트웨어 테스트만으로 실물 자세 안정화, 배터리 용량, 서보 피드백, 야외 주행 안전성이 입증되었다고 보고하지 않는다.
- 검증된 결과, 추정값, 가정, 차단된 검사, 사용자가 수행할 하드웨어 절차를 구분한다.
- 사용자가 직접 동작 시험을 하기 전 로봇을 고정하거나 들어 올리고, 주변을 비우며, 보정된 보수적 한계를 적용하고, 전원 차단 장치에 바로 접근할 수 있도록 안내한다. 짧은 시험 동안 사람이 즉시 전원을 끊을 수 있어야 한다.

## 오류 처리 및 인계

- 일시적 오류에 한해서 에이전트를 한 번 재시도한다. 인증·권한·사용량 한도 오류는 재시도하지 않는다. 누락된 작업을 보고하고 안전한 범위에서만 계속한다.
- 에이전트가 내리지 않은 결정을 추측해 채우지 않는다. 결과가 충돌하면 근거와 함께 모두 보존하고 통합 전에 인터페이스를 조정한다.
- 쓸 수 있는 결과가 없는 에이전트의 작업은 미완료로 표시한다. 성공한 것처럼 대체하지 말고 남은 작업을 사용자에게 알린다.
- 큰 중간 산출물은 `_workspace/{run-id}/`에 `01_{agent}_{artifact}.md` 형식으로 저장한다. 비밀 정보나 원본 자격 증명은 저장하지 않는다.

## 등록된 기능 작업: 수평 유지 비교 그래프와 관절 기구학 모형 (2026-11-11)

명세는 `robot-digital-twin` 스킬의 `references/level-comparison.md`, `references/kinematic-model.md`, `references/current-web-stack.md`에 있다. 원본 `software/web/`가 아니라 `software/robot_control_web/index.html` + `tools/servoInitPose/` + `software/usb_gateway/`가 작업 대상이다.

1. **사전 확인 (메인)**: 관절 방향은 사용자가 확인했다(2026-11-11: 네 무릎 모두 뒤쪽, BETA 증가 = 뒤로, ALPHA 증가 = 안으로, 좌우 어깨 간격 80 mm — `kinematic-model.md`에 기록). 남은 미확정 항목(앞뒤 어깨 간격, 조립 오프셋)은 화면과 보고에 "미확인"으로 남긴다.
2. **계약 (필요할 때만 `embedded` + `telemetry`)**: 모형에 서 있는 자세 보정을 반영하려면 상태 응답에 `standTrimDeg`를 추가한다(직렬 `STATUS`, Wi-Fi JSON, 게이트웨이, 버퍼 길이 재계산). 수평 비교는 기존 필드만으로 시작한다. 4 Hz보다 높은 샘플링이 필요해질 때만 로깅 계약을 따로 연다.
3. **구현 (`digital-twin`)**: 순기구학 순수 함수 → 모형 그리기 → 모델링 데이터 표 → 수평 비교 기록·통계·그래프 순서로 만든다. 한 단계가 끝날 때마다 `embed_page.py`와 테스트를 실행한다.
4. **QA (`qa`)**: 모의 상태로 페이지 하네스 테스트를 확장·실행하고, 필드 일치·안전 경로 불변·외부 리소스 없음을 확인한다.
5. **실물 (사용자)**: USB 게이트웨이 페이지에서 모니터링 상태로 먼저 본다. Wi-Fi 경로 반영(펌웨어 업로드), 수평 유지 켜기, 관절 방향 확인용 동작은 모두 사용자 승인 후에만 한다.

펌웨어를 바꾸지 않는 범위(2번 생략)라면 `digital-twin`과 `qa`만 호출한다.

## 테스트 시나리오

### 정상 흐름

요청: “MPU9250 자세 안정화, INA219 보행 전력 로깅, 웹 디지털 트윈과 원격 보행 제어를 추가해줘.”

기대 동작: 현재 펌웨어·웹 UI를 확인하고 버전이 지정된 텔레메트리 및 명령 의미를 합의한다. 펌웨어, 게이트웨이·로깅, 대시보드 작업을 조율하고 모의 환경에서 계약과 안전 동작을 검증한다. 빌드·테스트 결과와 하드웨어에서만 가능한 검증을 구분해 보고한다. 승인 없이 실물 로봇을 움직이거나 배포하지 않는다.

### 수평 유지 비교와 관절 모형

요청: “수평 유지를 켰을 때와 껐을 때 차이를 그래프로 비교하고, 서보 각도대로 움직이는 실제 형태의 다리 모형을 보여줘.”

기대 동작: 등록된 기능 작업 절차를 따른다. 관절 방향을 추측하지 않고 확인하거나 미확인으로 표시한다. 페이지는 외부 리소스 없이 유지하고 내장본을 다시 만든다. 모의 상태로 통계·순기구학 테스트를 통과시킨다. 비교 기능이 스스로 수평 유지나 보행을 켜지 않는다. 화면에 명령 각도 기준이라는 점과 4 Hz 샘플링 한계를 표시한다.

### 연결 실패

요청: “인터넷 연결이 끊겼을 때 웹에서 보행 명령을 보내도 계속 움직이지 않게 해줘.”

기대 동작: 게이트웨이와 펌웨어의 heartbeat·명령 최신성 경로를 추적하고 기기 측 감시 타이머 정지를 구현하거나 확인한다. 모의 연결 끊김을 시험하고 재연결 후 자동 활성화·재개가 없는지 확인한다. 실측이 필요한 물리적 타이밍 가정을 보고한다.

### 잘못되었거나 누락된 센서 데이터

요청: “INA219 값이 없거나 MPU9250 기울기 값이 오래되면 대시보드와 보행을 안전하게 처리해줘.”

기대 동작: 텔레메트리/UI에서 센서 상태와 데이터 노후도를 명시한다. 잘못되거나 오래된 자세 데이터가 실시간 값으로 보이거나 위험한 동작을 지속시키지 않도록 한다. 배터리 상태를 알 수 없는 경우 유효한 추정치와 구분한다.
